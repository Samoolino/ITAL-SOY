# ITAL-SOY — Institutional Quality-Gated Commodity Execution Infrastructure

**Status:** architecture population and process-flow verification stage.

ITAL-SOY is the enterprise control-plane project for integrating QMS, HACCP/CCP quality controls, compliance, traceability, RBAC, evidence management, automated/verifiable audit logging, quality-gated backward funding, and bounded commodity/trading/arbitrage execution.

The project is being populated from the established VITAL-SOY methodology while keeping ITAL-SOY as the enterprise integration and contract-construction layer.

## Core principle

**Frontend access is not contract authority.** SaaS RBAC, data scope and workflow permissions are evaluated before an authorized signer can invoke an on-chain role. Smart contracts remain the final deterministic enforcement layer.

## Quality funding classification

Required logs are necessary but are not sufficient for funding access.

| Tier | Required condition | Default policy parameter |
|---|---|---:|
| FULL | Required logs complete + HACCP/CCP passed + designated QA parameters match | 100% |
| CONDITIONAL | Required logs complete + specified control-point logic valid, with remaining assurance conditions conditional | governance-defined |
| MINIMUM | Required logs complete but designated QA parameters/control logic do not match | governance-defined |
| BLOCKED | Required required-log set incomplete or critical gate invalid | 0% |

The percentages are governance parameters. They must be configured by policy and tested before production activation.

`logs present != quality passed != funding eligible != authorized != executed`

## Automated and verifiable logging

Authoritative audit records are generated by backend state transitions, not manually written by frontend users. Each event is canonicalized, hashed, sequenced and linked to evidence. Batches may be anchored on-chain for independent verification. Idempotency, bounded retry and fail-closed rules apply to consequential funding and execution actions.

The Audit Evidence Pack is designed to contain JSON, CSV, PDF and manifest artifacts with deterministic hashes.

## Contract access model

```text
SaaS Identity
  → Organization
  → Application Role
  → Data Scope
  → Workflow Permission
  → Authorized Wallet / Signer
  → On-chain Role
  → Contract Function
  → Policy + Evidence Gates
```

Representative roles: GOVERNANCE_ADMIN, QA_LEAD, COMPLIANCE_OFFICER, RISK_OFFICER, ECONOMIC_ANALYST, TRACEABILITY_OFFICER, AUTHORIZER, STRATEGY_OPERATOR, RESERVATION_OPERATOR, EXECUTOR, AUDITOR and DEPLOYMENT_ADMIN.

QA_LEAD, AUTHORIZER and EXECUTOR are deliberately separated. Strategy and treasury authority are also separated.

## Remix / contract workspace

Remix is a development, inspection and controlled deployment workspace for the contract library. It is not the SaaS authorization boundary. Production authority remains governed by the deployment manifest, role wiring, signer policy and on-chain access controls.

## Verification gate

Before live venue/router adapters are promoted:

**Foundry configuration → mocks/fixtures → unit tests → invariant tests → deterministic deployment → role-state assertions → quality-gate assertions → controlled-fork execution → machine-readable verification report → audit-anchor verification.**

## Contract construction boundary

The planned institutional contract set is:

1. Quality Control Point / evidence commitment
2. Quality Funding Gate
3. Funding Eligibility Registry
4. Backward Funding Controller
5. Treasury / Execution Funding Vault
6. Execution Authorization / Nonce control
7. Audit Anchor
8. Primary Arbitrage execution boundary
9. Auxiliary Commodity execution boundary
10. Auxiliary Trading execution boundary
11. Adapter registry / venue policy boundary
12. Settlement and reconciliation controls

No live financial adapter is considered production-ready merely because its contract exists; every adapter must pass the same policy, authorization, quality, funding and verification boundaries.
